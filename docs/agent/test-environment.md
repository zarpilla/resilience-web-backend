# Test environment — https://w.resilience.earth

A copy of the site, on the same server as production, used to:

- try content changes (people or AI agents) before doing them in production;
- try code from the `develop` branch before merging it to `main`.

| | Production | Test |
|---|---|---|
| Front end | https://resilience.earth | https://w.resilience.earth (basic auth, `noindex`) |
| Strapi admin | https://api-w.resilience.earth/admin | https://w.resilience.earth/admin |
| REST API (`RW_API_URL`) | https://api-w.resilience.earth | https://w.resilience.earth |
| Code | branch `main` | branch `develop` |
| Database | `resilience_web2` | `resilience_web_test` (same Postgres container) |
| Uploads | production folder | own folder; missing files are served from production (read only) |
| E-mails (forms) | sent | **disabled** (the lead/subscription is saved, the visitor sees an error) |

- The test front end asks for a user and password (same as the old w.resilience.earth). The
  API, admin and uploads are not behind basic auth (Strapi has its own login), but every
  response carries `X-Robots-Tag: noindex` and `robots.txt` disallows everything, so search
  engines don't index the test site.
- Admin users are the production ones (the database is a copy).
- API tokens are **different** in each environment (different salt). A test token only works
  on test. Tokens are never written in this repository: ask the developer, who keeps them
  outside the repositories.

## Server layout (`/var/www/resilience-web/test/`)

```
resilience-web-backend/    checkout of develop (src/ and config/ are mounted in the container)
resilience-web-frontend/   checkout of develop (built into the test front-end image)
env/backend.env            secrets for test Strapi (generated by setup.sh, chmod 600)
env/frontend.env           public URLs for the test front end
data/uploads/              files uploaded in test
backups/                   database dumps (last 10)
```

Containers: `re_web_back_test` (127.0.0.1:1351), `re_web_front_test` (127.0.0.1:3004).
Files: `tools/test-env/` (compose files, nginx site, scripts).

## Operations (on the server, as `resi`)

```bash
T=/var/www/resilience-web/test/resilience-web-backend/tools/test-env
$T/deploy.sh        # deploy the latest develop (backend + front end)
$T/refresh-db.sh    # replace test data with a fresh copy of production (keeps a dump)
docker logs -f re_web_back_test   # Strapi rebuilds its admin at start: ~2-3 min
```

First installation: `tools/test-env/setup.sh` (no sudo) + the nginx site
`tools/test-env/nginx-w.resilience.earth.conf` (needs sudo; instructions inside the file).

Resources: test adds ~0.5 GB RAM at rest. A Strapi start uses a lot of CPU for 2–3 minutes
(admin build): avoid restarting test and production at the same time.

## Workflow for content changes (people or agents)

1. `refresh-db.sh` if test is out of date with production.
2. Make the change on test (`RW_API_URL=https://w.resilience.earth` + a test token, or in the test admin).
3. Review it on https://w.resilience.earth.
4. Apply the same change to production. With the CLI: `export` from test, then `push` to production
   with `--yes` (the person must approve). Media ids may differ if files were uploaded in test:
   upload them to production first and use the production ids.

## Workflow for code

1. Work on a feature branch, merge into `develop`, push.
2. `deploy.sh` on the server → check https://w.resilience.earth.
3. Merge `develop` into `main` → production deployment (see `docs/tasks/DESPLEGAMENT-2026-10.md`).
